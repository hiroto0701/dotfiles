# C4 アーキテクチャを HTML で描く

## 概要

C4 の L1〜L3 を、インライン SVG の HTML 1ファイルにライトモード固定で描く。表記は同梱の `template.html` で固定し、レイアウトは同梱の `check.mjs` で機械的に検査する。L4（Code）と配置図は描かない。

## 手順

1. **既存資料を探す。** リポジトリ全体から `*architecture*`、`docs/**`、README の構成図（mermaid を含む）を探す。
   - 既存の C4 HTML があれば、新規に作らずそれを更新する。
   - C4 でない構成図は、根拠の一つとして読む。コードとの食い違いは「前提と未確認事項」に書く。
   - リポジトリの CLAUDE.md が読むなと定めた場所は読まない。そこで分からない関係は推定として扱う。
2. **種別と基準コミットを決める。** `git rev-parse --short HEAD` を `<main data-c4-commit>` とメタ欄に入れる。git 管理外なら `none` とし、メタ欄にその旨と、読んだファイルの最終更新日を書く。
   - as-is: 基準コミットのコードを描く。
   - to-be: 設計書の最終形を描く。移行中に一度だけ動くもの（移行バッチなど）は描かず、列挙だけする。設計書が詳細を別の設計書や README に任せている部分は、それらも根拠にして「参照した資料」に載せる。
   - to-be の状態クラス（`new` / `changed` / `removed`）は「比較の基準」と比べて付け、比較の基準をメタ欄に書く。既定は基準コミットのコード。設計の一部がすでに実装済みなら、設計着手前のコミットや本番の構成を比較の基準にしてよい。段階移行の設計なら、タグに段階名を添える（例: 新設 SP3）。
   - to-be で、設計の対象外かつ変更のない Container は省き、省いたものを「前提と未確認事項」に列挙する。
3. **要素を判定する。** 下の判定表に従う。根拠のファイルパスを要素表の「根拠」列に書く。
4. **図の分け方を決める。** 1枚の図の `g.el`（人物、外部システム、Container、Component のすべて）は15個まで。
   - まず同種のもの（バッチ群、運用補助の関数群、生成ファイルのバケット群）を1つの箱にまとめる。
   - それでも超えるなら、L2 を観点ごとに L2-a、L2-b…と分け、全 Container を一覧表に載せる。分けた場合、全体図は描かない。
   - L3 は中心になる Container だけ描く（複数あれば1つずつ別の図にする）。周囲の Container と外部システムも15個に含む。
5. **書く。** `template.html` をコピーし、見本の記法（`g.el` / `.shape` / `g.rel` / `g.boundary`）を守る。`<title>`、`<h1>`、メタ欄、見本の図と表はすべて置き換える（残っていると check.mjs が落ちる）。
   - 箱の幅は文字数から見積もる。日本語は1文字が文字サイズとほぼ同じ幅（12px なら約12px）、英数字は約0.55倍。左右に16px以上の余白を足す。
   - `g.rel` の線は M / L / H / V だけで描き、`transform` を付けない（交差検査のため）。
   - L3 の Component 間の関数呼び出しは tech を省いてよい。省いたらキャプションにそう書く。
   - 図はテンプレートの CSS とクラスだけで描く。色を足さない。
   - ページはライトモード固定。`<html data-theme="light">` を残し、ダーク用の CSS を足さない。
6. **検査する。** `node <このスキルのディレクトリ>/check.mjs <出力.html> [スクリーンショット出力先]` を実行し、problem を0にする。warning（矢印の交差、線がラベルを貫く）は配置を変えて減らし、残すものは理由を説明できるようにする。最後にスクリーンショットを見て、次を確かめる。
   - 矢印の始点と終点が、意図した箱に付いている
   - 線が境界のラベルや別の箱を横切っていない
   - 推定の関係に「推定」と書いてある
7. **保存する。**
   - as-is: `docs/architecture/c4.html`（日付なしで上書き更新する）
   - to-be: `docs/architecture/YYYY-MM-DD-<topic>-c4.html`

## 判定表

| 対象 | 扱い |
|---|---|
| 自分たちがデプロイする実行単位（サービス、関数、ジョブ、SPA、モバイルアプリ） | Container。同じコードでも、入口と実行者が違えば分けてよい |
| 自分たちのデータを持つ DB、バケット、キャッシュ | Container（データストア） |
| LB、CDN、API Gateway、WAF、DNS | Container にしない。矢印の tech に `via Cloud LB` と書く |
| キュー、トピック（Pub/Sub、Cloud Tasks、SQS） | Container にしない。矢印を `async` にし、tech に `via Pub/Sub <名前>` と書く。自分自身に戻る経路は説明文に書く |
| スケジューラ（Cloud Scheduler、cron、GAS トリガー） | 箱にしない。起動される Container の説明に「毎日6時に起動」と書く |
| 設定・シークレットの置き場、ログ基盤、監視 | 箱にしない。必要なら説明文か矢印の tech に書く |
| 他チームのシステム、SaaS、マネージド AI API | 外部システム |
| 同じ製品で所有者が混在する（例: BigQuery） | 所有者で分ける。自分たちのテーブル＝データストア、他チームのもの＝外部システム |
| 同じイメージを複数リージョンに配置 | 1つの Container。配置の違いは説明に書く |
| Component | 外から呼ばれる入口（ハンドラ、ミドルウェア、ジョブ）か、責務のまとまり。1つの関数、型定義、スキーマファイル、設定、テストは Component にしない。目安は1 Container あたり5〜12個 |

## よくある間違い

| 間違い | 直し方 |
|---|---|
| 大きいシステムの L2 を1枚に詰め込み、矢印が交差だらけになる | 手順4で分ける。check.mjs の `elements (max 15)` は無視しない |
| インフラやキューを箱にして L2 が膨らむ | 判定表のとおり矢印の tech に移す |
| L3 がファイル一覧や関数一覧になる | 責務でまとめる。ファイル名は要素表の根拠列に書く |
| 推定の関係を確定のように描く | 矢印の tech に「推定」と書き、「前提と未確認事項」に理由を書く |
| 境界のラベルを下端に置き、矢印のラベルとぶつかる | 境界のラベルは内側の左上に置く |
